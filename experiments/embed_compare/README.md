# 임베딩 모델 비교 실험 — KIVI · InfiniGen 논문 검색

2026-09-21 · 로컬 macOS arm64 (MPS) · `langgraph-v1` venv · 실행자: 유진

## 목적

RAG 파이프라인의 오픈소스 임베딩 모델을 **우리 코퍼스·우리 질의**에서 실측해 선정.
리더보드 순위가 아니라 "한국어 질의 → 영어 논문 검색"이 되는지를 본다.

## 설정

| 항목 | 값 |
|---|---|
| 코퍼스 | `data/papers/kivi.pdf` (15p) + `infinigen.pdf` (18p) = 33p |
| 청킹 | 페이지 텍스트 → 600자 슬라이딩, overlap 100 → **299 chunks** |
| 평가셋 | `eval_set.json` — **20문항** (논문당 10), 한국어/영어 질문 쌍 + gold 문구 |
| 정답 판정 | top-k 청크 중 gold 문구(원문에서 복사, 공백·대소문자 무시)를 포함한 청크가 있으면 Hit |
| 지표 | Hit Rate@4, MRR@4, 인덱싱 시간 |
| 검색 | dense 단독 (cosine). BM25 하이브리드는 파이프라인 단계에서 별도 측정 |

## 후보와 선정 이유

| 모델 | 차원 | max_seq | 크기 | 다국어 | 검증하려는 질문 |
|---|---|---|---|---|---|
| `BAAI/bge-m3` | 1024 | 8192 | 2.27GB | O | 1순위 가설 (다국어 + 긴 컨텍스트) |
| `intfloat/multilingual-e5-large` | 1024 | 512 | 2.24GB | O | 같은 급 다국어인데 512 — 다국어면 다 비슷한가 |
| `BAAI/bge-base-en-v1.5` | 768 | 512 | 0.44GB | X | 문서가 영어니 영어 전용·경량으로 충분한가 |
| `nomic-ai/nomic-embed-text-v1.5` | 768 | 8192 | 0.55GB | 제한적 | 경량 + 긴 컨텍스트로 충분한가 |

## 결과

| 모델 | ko Hit@4 | ko MRR@4 | en Hit@4 | en MRR@4 | 인덱싱 |
|---|---|---|---|---|---|
| **`BAAI/bge-m3`** | **0.65** | **0.50** | **0.65** | **0.50** | 15s |
| `intfloat/multilingual-e5-large` | 0.55 | 0.48 | 0.50 | 0.50 | 19s |
| `BAAI/bge-base-en-v1.5` | 0.35 | 0.24 | 0.45 | 0.42 | 5s |
| `nomic-ai/nomic-embed-text-v1.5` | — | — | — | — | `einops` 미설치로 미실행, 제외 |

## 해석

1. **BGE-M3 채택.** 한국어 질의 Hit@4 0.65로 2위(e5) 대비 +0.10, MRR도 최고
2. **한↔영 차이 없음** (0.65 / 0.65) → cross-lingual 검색 성립. 에이전트 질의를 한국어로 써도 됨
3. **영어 전용 모델은 한국어 질의에서 반토막** (0.45 → 0.35, MRR 0.42 → 0.24) → "문서가 영어라 다국어 불필요"는 질의를 영어로 고정할 때만 성립. 우리 파이프라인은 한국어 질의라 다국어 필수
4. 같은 다국어여도 e5(512)는 M3(8192)보다 낮음 — 모델 차이가 있고, 긴 청크 대응 여유도 M3가 큼
5. 절대값 0.65는 dense 단독 + 부분일치 기준. 파이프라인은 BM25 하이브리드라 고유 용어(per-channel, prefetch, UVM)에서 올라갈 것으로 예상 → 개발 단계에서 같은 20문항으로 재측정해 README에 기재

## 수치가 이렇게 나온 이유 — 문항별 분석 (BGE-M3, ko)

| 논문 | Hit@4 | 실패 문항 (rank) |
|---|---|---|
| KIVI | **9/10** | residual length R=128 (7위) |
| InfiniGen | **4/10** | 3.00× 성능 향상 (>10), PCIe 병목 (>10), CPU pool (6위), RTX A6000 (>10), UVM 베이스라인 (>10), counter-based 정책 (>10) |

**1. 0.65는 거의 InfiniGen에서 깎인 것.** KIVI는 0.9.

**2. 실패 문항은 전부 "고유명사·숫자·설정값" 질문.** A6000, UVM, counter-based, 3.00×, R=128 — 이런 건 **의미가 아니라 정확한 토큰**을 찾아야 하는데, dense 임베딩은 "주제가 비슷한 청크"를 찾는 도구라 약함. 예: "PCIe 병목" 질문에는 오프로딩·전송을 얘기하는 청크가 10개 넘게 있어서, 정확히 그 문장이 있는 1개 청크가 묻힘.

**3. InfiniGen이 더 약한 구조적 이유.** 18p·시스템 논문이라 배경 설명이 길고 같은 주제(오프로딩, PCIe, 정확도)를 여러 절에서 반복 → gold 문구가 든 청크(대부분 1~2개)와 의미상 비슷한 청크가 많아 순위가 밀림. KIVI는 15p·알고리즘 논문이라 각 사실이 한 곳에 집중.

**4. ko = en 인 이유.** 틀린 문항이 거의 같음 → BGE-M3가 한국어 질문과 영어 질문을 같은 벡터 공간으로 보냄. 언어가 아니라 질문 유형이 성패를 갈랐다는 뜻.

**5. bge-base-en이 ko에서 0.35인 이유.** 영어 WordPiece 토크나이저라 한국어가 의미 없는 조각으로 쪼개짐. 0이 아닌 건 질문 안의 영어 용어(KIVI, Key cache, GPU)만으로 일부 맞춘 것.

**시사점**
- 실패 유형이 lexical이라 **BM25 하이브리드에서 크게 회복될 것** (BM25는 "A6000", "UVM" 같은 토큰을 정확히 잡음). 파이프라인이 EnsembleRetriever인 이유가 실측으로 확인됨
- 기술 조사 에이전트가 실제로 물을 질문("어떤 GPU로 실험했나", "베이스라인은")이 바로 이 유형이라, 평가셋이 현실적이었다는 뜻이기도 함
- 그래도 dense 모델 간 순위(M3 > e5 > en)는 같은 문항으로 비교했으니 유효

## 재실행

```bash
cd langgraph-v1/experiments/embed_compare
../../.venv/bin/python embed_compare.py \
  --pdf ../../data/papers/kivi.pdf ../../data/papers/infinigen.pdf \
  --eval eval_set.json
# 일부만: --models BAAI/bge-m3 BAAI/bge-base-en-v1.5
# nomic 포함하려면: uv add einops
```
